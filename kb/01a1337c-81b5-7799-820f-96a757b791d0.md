# Build cape

The build records the owner's seeded id as `owner` and its cape root doc's name as `shortName`, apart from the build id and the hero's long repo name for it; help heads the cape by the short name. It asks describe-cape-source for each kind's version, so the manifest and the bundle carry them.

A build shipped with the running core is taken before any clone (shipped-cape-builds): for a repo cape at a ref that is a commit, as a `.cape` pin is, build looks in `capes/` beside the core's built file (`dist/capes/` in a package), which holds a `manifest.json` of builds and each build's `<id>.js`, as a bridge keeps its own. A build there of the same repo, at that commit, made by this core, is copied into the bridge with every build it needs and recorded in its manifest, and the clone is never made; one that does not match, or needs a build that is not shipped, is built as below.

The clone lives under `.nosedive/capes/src/<repo id>` and is fetched on each build, its origin set first to the repo doc's, so a cape whose `meta.remotes.origin` changed is fetched from where it is now. The repo must be a cape, its root of core's kind `cape`, and pass the cape source check. A cape whose action, function and migration docs, or whose root, are bare core kinds with no canonical entry for core was written before canonical kinds, and the build refuses it: `<cape> at <commit> predates canonical kinds: its <n> action/function docs and root do not name core; seed it with this core (the canonical-kinds migration) and push`. Likewise a cape any of whose kind docs still carries `meta.durable` was written before a kind's durability was read from its Done when, and would be misread, so the build refuses it: `<cape> at <commit> predates durability read from Done when: its kinds <names> still say meta.durable; seed it with this core (the durable-from-done-when migration) and push`.

A repo cape is built at its ref, from its clone or shipped, whether or not the hero's workspace holds a checkout of its repo: a workspace checkout is never a build source, so every build of a hero runs the same cape code and a pin bump takes effect (pin-always-wins). Imported capes follow the same rule. To run a cape's unlanded work, re-attach it at its branch (`pass --attach-cape <repo> --ref <branch>`), which pins the branch's tip, or wear it as a local cape.

A local cape, a directory of the hero seeded as a cape (see configured-capes), is built from that directory, logging its path, and never fetched or checked out: its working tree, its id covering the contents and paths of tracked and unignored untracked files in the directory, assets and deletions included, so uncommitted changes invalidate the cache, but not the hero's HEAD, which every commit moves, its version `working tree`. Its repo id is its root doc's quid and its name that doc's name.

A cape imports `i<id>` from `nosedive-core`, or from another cape by its repo's name in the bridge kb (`from "nosedive-crud"`). Each cape it imports is built first, at the commit or ref the target root's link to that repo pins (see configured-capes), or its trunk when it wears none; capes that import each other in a cycle are refused. Each imported id must be a doc of what it comes from and a link of one of the cape's own action docs. The import is bundled as a lookup of `uuidv5(<doc id>, <id of what it comes from>)` in that cape's index, so the built cape refuses to run against any other core or other builds of the capes it imports.

A cape also takes core's other named exports, such as `import { assertPublished, pinOf } from "nosedive-core"`: every value a core source file exports besides its default function (see describe-cape-source's `namedExports`), which core's `named` carries and its `dist/core.js` and `dist/core.d.ts` export, types included. Only core has them: the build refuses a name core does not export, and the bundle reads each from the running core's `named`, so these too tie the cape to the core it runs on.

Before bundling, the clone's npm packages are installed with install-cape-packages; bundle-cape bundles what the code imports of them, and its assets.

A cape whose id is already built and recorded is not built again. Building needs esbuild installed next to nosedive, and npm when the cape has packages.
