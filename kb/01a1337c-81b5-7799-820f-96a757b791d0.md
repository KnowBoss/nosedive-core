# Build cape

The build records the owner's seeded id as `owner` and its cape root doc's name as `shortName`, apart from the build id and the hero's long repo name for it; help heads the cape by the short name. It asks describe-cape-source for each kind's version, so the manifest and the bundle carry them.

The clone lives under `.nosedive/capes/src/<repo id>` and is fetched on each build. The repo must be a cape, its root of core's kind `cape`, and pass the cape source check. A cape whose action, function and migration docs, or whose root, are bare core kinds with no canonical entry for core was written before canonical kinds, and the build refuses it: `<cape> at <commit> predates canonical kinds: its <n> action/function docs and root do not name core; seed it with this core (the canonical-kinds migration) and push`.

When `<workspace>/<repo name>` exists, build uses that checkout instead and logs its path. Its current working tree takes precedence over the configured ref: build never fetches or checks out that workspace repo. The build id includes HEAD and the contents and paths of tracked and unignored untracked files, including assets and deletions, so uncommitted changes invalidate the cache. Imported capes follow the same rule. Without a workspace checkout, the configured remote and ref still apply.

A cape imports `i<id>` from `nosedive-core`, or from another cape by its repo's name in the bridge kb (`from "nosedive-crud"`). Each cape it imports is built first, at the ref the bridge's config uses for that repo, or its trunk when config names none; capes that import each other in a cycle are refused. Each imported id must be a doc of what it comes from and a link of one of the cape's own action docs. The import is bundled as a lookup of `uuidv5(<doc id>, <id of what it comes from>)` in that cape's index, so the built cape refuses to run against any other core or other builds of the capes it imports.

A cape also takes core's other named exports, such as `import { assertPublished, pinOf } from "nosedive-core"`: every value a core source file exports besides its default function (see describe-cape-source's `namedExports`), which core's `named` carries and its `dist/core.js` and `dist/core.d.ts` export, types included. Only core has them: the build refuses a name core does not export, and the bundle reads each from the running core's `named`, so these too tie the cape to the core it runs on.

Before bundling, the clone's npm packages are installed with install-cape-packages; bundle-cape bundles what the code imports of them, and its assets.

A cape whose id is already built and recorded is not built again. Building needs esbuild installed next to nosedive, and npm when the cape has packages.
