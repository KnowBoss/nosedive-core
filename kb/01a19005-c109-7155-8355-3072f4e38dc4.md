# Commit subject

Every commit nosedive makes is grouped by the feat it serves, when it serves one: `feat(<feat name>): <action> <what>`. The default function builds it from a bridge, the action, what it did, and the ids of the docs it touched; `subjectLine` builds it from a feat name already known, as the work loop does. With no feat name the subject is `<action>: <what>`, and nothing refuses.

`featNameOf` walks the feat tree once (see feat-tree), never the whole kb, and finds the feat's name, the first of these that answers:

- The dive this worktree holds: the open dives whose `meta.diver` is this worktree's holder token (`holderToken`: the git `user.email` and a hash of the hero's top directory and branch). One names its `meta.feat`. Several make the subject plain, since no feat is the work's; the work cape's dive-on-deck refuses them. A dive held under another worktree's token is no one's here.
- Of the touched docs, in order, the first that has a feat: the doc itself when the feat tree holds it; else a feat it links to, through a link whose rel ends `.feat` or `.spec`; else a feat that links to it so, as a feat links `closed.spec`, `open.spec` or `legacy.spec` to a decision or question that links nothing back. A root of the hero has no feat: its `.feat` links go down to the feats it holds, none of which an edit of the root serves, so it is passed over.

A doc in a workspace checkout is looked up through the hero, like any other.
