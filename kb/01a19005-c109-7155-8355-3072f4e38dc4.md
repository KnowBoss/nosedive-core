# Commit subject

Every commit nosedive makes is grouped by the feat it serves, when it serves one: `feat(<feat name>): <action> <what>`. The default function builds it from a bridge, the action, what it did, and the ids of the docs it touched; `subjectLine` builds it from a feat name already known, as the work loop does. With no feat name the subject is `<action>: <what>`, and nothing refuses.

`featNameOf` finds the feat's name, the first of these that answers:

- The dive this worktree holds: an open doc named `dive` in a root of the hero whose `meta.diver` is this worktree's holder token (`holderToken`: the git `user.email` and a hash of the hero's top directory and branch), and whose `meta.feat` is a doc the hero holds. With several held, the first by file name.
- Of the touched docs, in order, the first that has a feat: the doc itself when it is a feat, which is a doc the hero's roots reach through links whose rel ends `.feat` (a root of kind cape and `parent.feat` links aside, as work reads the feat tree); else the first feat found through its own links whose rel ends `.feat` or `.spec`, in either direction (`parent.feat`, `child.feat`, `closed.spec`, `open.spec`), to a doc the hero holds.

A doc in a workspace checkout is looked up through the hero, like any other.
