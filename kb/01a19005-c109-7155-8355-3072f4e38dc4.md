# Commit subject

Every commit nosedive makes is grouped by the feat it serves, when it serves one: `feat(<feat name>): <action> <what>`. The default function builds it from a bridge, the action, what it did, and the ids of the docs it touched; `subjectLine` builds it from a feat name already known, as the work loop does. With no feat name the subject is `<action>: <what>`, and nothing refuses.

`featNameOf` walks the feat tree once (see feat-tree), never the whole kb, and finds the feat's name, the first of these that answers:

- The feat the hero's branch names: a branch that ends with the quid of a feat the feat tree holds, after a slash or a dash, as a work loop's branch for a feat's work names it (`nosedive-<token>-<dive id>`, a dive being a feat its feat links as `dives.feat`). Core reads no kind or meta for it: what the branch names is a feat by the tree, and its name is the feat's. A branch naming a doc the tree does not hold, but a walked doc other than a root links by a rel its non-durable kind names in `meta.next`, groups under that doc's own name, and a doc with no name groups nothing, never `feat(undefined)`. That is the one place a kind is read, so `featNameOf` takes the capes (optional; without them only the tree counts), and it reads a doc's kind only when nothing else answered for it. That costs one kind listing for that doc, and, the first time a doc needs it, one pass over the links of the docs the walk already read to index who links what; each later doc is a lookup in that index.
- Of the touched docs, in order, the first that has a feat: the doc itself when the feat tree holds it, by its own name; else a feat it links to, through a link whose rel ends `.feat` or `.spec`; else a feat that links to it so, as a feat links `closed.spec`, `open.spec` or `legacy.spec` to a decision or question that links nothing back. Failing those, a walked doc that links it by a rel its non-durable kind names in `meta.next` (see next), as a feat links a dive its kind says is work hung there (drop-takes-declared-links). A root of the hero has no feat: its `.feat` links go down to the feats it holds, none of which an edit of the root serves, so it is passed over, and a root is never the holder a commit is grouped under: where a root and a feat both link a doc by a declared rel, the feat is found, whichever the walk met first.

A doc in a workspace checkout is looked up through the hero, like any other.
