# The root of a ship: where pilots work, with the workspace other repos are checked out in

# Ship

Where pilots work, and the repo nosedive resolves when it runs. `nosedive seed` makes one: `ship` is the default root kind. Its config names its root as `ship: <quid>`.

Only a ship has a workspace, at the path its root's `meta.workspace` gives (`./workspace` when seeded). Seed makes the folder, with a `.gitignore` of `*` inside, so nothing checked out there is committed and the repo's own `.gitignore` is left alone; when the path changes, the next seed moves the workspace. Writing a doc into a repo checked out there, with `crud <repo>:<kind>`, refuses anywhere else. A legacy `base` root that carries `meta.workspace` is read as a ship, so bridges seeded before ships keep their workspace.

A ship declares kinds of its own, beside those of the capes it uses; a base it works with declares none.

## Its own actions

A ship can carry actions and functions of its own, in its kb and `src/` as a cape does, which scaf scaffolds and the check checks. They are the ship's alone: no other ship can add them, as it can a cape. Its commands run as `nosedive <name>` from the ship or its workspace, and help lists them under the ship's name, after core's; its gates are among those pass reaches.

Its code is built from the working tree, not from a commit, into `.nosedive/capes/<id>.js`, with `<id>` covering the core and every code doc and file, so an edit is built on the next run that needs it. It imports from core only.

Every run that needs the ship's code, each `pass`, `help` and any command core lacks, learns which docs are code from `src/`, whose files are named by doc id, and reads only those, never the rest of the kb. So a doc with no files yet is no part of the build and blocks nothing until scaf writes them; the check, which reads the whole kb, runs only when the code changed and is rebuilt.
