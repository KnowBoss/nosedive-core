# Canonical kinds

Under canonical kinds a bare kind is the holding repo's own, and a doc of anyone else's kind says whose in a scope entry, `<owner's seeded id>: {canonical: true, version: <schema commit>, schema: <schema digest>}`. This brings a repo's docs there. It looks at every root of the repo, which share its kinds.

1. **Root becomes base.** A doc of kind `root` becomes `base`; a canonical entry it had for core is dropped, its `version` and `schema` with it, to be given again below with those of `base`.
2. **Names.** Each kind name the docs use, collected across all roots, that the repo does not declare itself (in its `.nosedive/kinds/`, or as a kind doc in a root):
   - A cape the repo wears declares it, by its newest build here: every doc of it gets an entry for that cape's owner, with the version the build recorded for the kind. A name two worn capes declare is given to neither, and is declared in the repo as below.
   - It is one of the five kinds core's code reads, `action`, `function`, `cape`, `migration` and `base`: every doc of it gets an entry for core, always. If a worn cape declares one of these names too, the migration says the cape clashes with core and still gives core's entry.
   - Otherwise the repo gets one kind doc of that name in `.nosedive/kinds/`, its body listing the meta fields seen in use across all roots, each with one sample value. When core declares the name without its code reading it, `memo`, the kind copies core's declaration: its schema and its `durable`, so a repo's memos are as durable as core's. When nothing declares it, as with legacy names such as `feat`, its schema is open (`{type: object}`) and it is not durable, and its body asks the pilot for a definition. The pilot closes it, or moves its docs to a kind that is declared.
3. **Left alone.** Docs in `.nosedive/`, which are core's by place; docs of kind `kind` or `repo`, which are too; docs that already carry a canonical entry; and the repo's own kinds. In core's own repo those include `action`, `function`, `migration`, `cape` and `base`, so core's docs get no entries.

It commits once, as `migrate: canonical-kinds`, and changes nothing when run again: what it declared is declared, and what it gave an entry has one.

An entry is the kind's pin, `version` and `schema` digest, as `pinOf` gives it (see find-kind): a version is only a commit on its owner's origin trunk or a feat's work branch, so a kind whose schema commit is neither cannot be pinned.

It waits for the capes. When any cape worn by any root has no build here, or a build that records no `owner` or `kinds` (one made by an older core), what that cape declares is not known, and a kind of its could be declared in the repo by mistake. So the migration writes nothing, says it is waiting for those capes to build, naming them, and its quid is not appended to config `migrations`, so it runs again at the next chance. It waits in the same way when it cannot pin a kind it would give an entry for: it writes nothing, appends no quid, and says which kinds' schemas must be pushed first. Waiting is not an error, and the migrations after it wait with it. Seed gives it that chance: it runs pending migrations, builds the capes, and runs them once more, so on a first seed with a new core the migration runs right after the capes it needs are built. A repo that wears no capes runs it in the first pass.
