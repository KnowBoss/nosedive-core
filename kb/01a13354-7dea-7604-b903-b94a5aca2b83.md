# Crud

## Usage

`crud` alone lists the kinds there are, as list-kinds finds them: the repo's own kinds, bare, then each cape it wears that declares kinds, core first, with every spelling that reaches each of its kinds.

```text
my-hero
  idea

core
  (core|nosedive-core|01a1336b-c0b8-7cde-b7c6-285196062297):memo
```

`crud <quid>` prints a doc: from the bridge's kb, then the repos checked out in its workspace (see locate-kb-doc), then the docs of the capes that are loaded, then those of every cape the bridge wears that has a build for this core, so a cape's own docs, its migrations' included, can be read anywhere it is worn. The edits below find their doc the same way, and commit in the repo it lives in. They refuse a doc git does not track, such as a tool's local copy, before writing anything, since its change could never be committed.

`crud <kind> <gist>...` mints a doc of that kind in the target (see launch's `--at`), the primary root's directory unless another is selected, and commits in the git repo holding it: `nosedive --at workspace/<repo> crud <kind> ...` writes into a checkout, at any directory of it, seeded or not. Docs of core's own kinds, `core:kind` and `core:repo`, go in the hero's `.nosedive/kinds/` and `.nosedive/repos/` instead, and refuse a selected target, since the hero reads its kinds and repos only from there.

A kind is spelled as find-kind takes it. A bare kind is the repo's own and nothing else, so core's memo is `core:memo`; `<short>:<kind>`, `<long>:<kind>` and `<quid>:<kind>` are a cape's, by the name of its cape root doc, the name of the repo doc that registers it, or its owner's seeded id. A spelling no kind answers to is refused, naming those that reach a kind of that name; a bare kind the repo does not declare is refused, naming the kind and saying the hero can declare one of that name, and how a cape that declares it is spelled if one does. A kind doc named `kind` is refused: only core declares the kind of kinds. Its name is `--name`, or the gist's first words slugged with the id's last six characters; its title is made from `--name` when one is given, else the gist (see mint-kb-doc); and its meta is whatever `--meta <source>` reads, so a kind with required meta can be minted.

`crud core:repo <gist>... --name <name>` registers a repo, and refuses, writing nothing, unless `--name` is given and unique among the hero's repos, and `meta.remotes.origin` is given and `git ls-remote` reaches it. It makes nothing else: creating a bare repo somewhere is a cape's job.

The `--meta`, `--scopes` and `--links` usages read a YAML or JSON mapping from `<source>` (`-` for stdin) and merge it into that field, then commit:

- `--meta`: a JSON merge patch onto `meta`.
- `--scopes` and `--links`: keyed by repo or link target, a link to a doc in another repo keyed `<repo>:<path>`, its path in that repo; each value is merged onto that entry, a new key is appended, and `null` removes the entry. An entry the patch does not name keeps its written form, and one left with no fields is written as `{}`.

`--parent <parent>` makes `<parent>` the doc's only `parent.feat`: its other `parent.feat` links go, with those parents' `child.feat` links back to it, and `<parent>` gains a `child.feat` link to it, all in one commit. Both docs must be in the same kb, and a parent that is the doc itself or under it is refused, as is a non-durable parent of a durable doc that is no root (see kind). That rule holds for every edit that adds a `.feat` link, `--links` and `--batch` included (see edit-kb-docs). Each new link is keyed by its target's path from the repo root: `bridge/<id>.md` in a hero repo, `kb/<id>.md` in a cape.

Whatever a doc's kind is, crud checks its `meta` against that kind's schema when it mints the doc, changes its meta, or changes its kind (`--kind <kind>`). The kind is the doc's own (see doc-kind), found in the terms of the repo that holds the doc when that is seeded (see Writing a doc). A kind nothing declares cannot be minted or changed to, and the meta of a doc whose kind nothing resolves is refused too, naming the kind and saying the hero can declare one of that name.

A kind's schema can require a meta field to contain the quid of a doc of a particular kind. For example, `question: {type: string, kind: question}` under `properties` requires that `meta.question`, when present, is text containing a quid resolving to a doc whose frontmatter says `kind: question`; adding `question` to `required` makes the field mandatory. Crud searches the doc's kb and the bridge's kb first, then the hero and its workspace, then loaded capes. An invalid quid, missing doc or wrong kind refuses the write with an error at the field's path. This checks outgoing references when the owning doc's meta is validated; it does not revalidate incoming references when their target changes kind or is deleted.

In a batch, reference-kind validation sees every edited target's final kind, regardless of edit order. A failed reference check writes and commits nothing from the batch.

`--gist <gist>` and `--name <name>` replace those fields; quote a gist of more than one word. `--kind <kind>` takes a kind spelled as a mint takes it, and writes the doc's scopes as a mint would: the canonical one names the kind's owner unless that is the repo that holds the doc, and a canonical one the doc had is gone.

A doc's body is its title, the one `# ` heading that starts it, then everything under it, and crud keeps the title apart so no edit loses it:

- `--title <title>` sets the title, adding one when the doc has none.
- `--body <source>` replaces everything under the title with the text `<source>` holds (`-` for stdin, else a file), as text, not YAML. An empty source leaves only the title.
- `--section <heading> <source>` replaces the `## <heading>` section, up to the next `## `, with that text, or appends it when the doc has no such section; an empty source removes it. On a `kind` doc, `--section "Drop when"` decides the kind's durability: adding the section makes it passing work, removing it makes it durable, and crud says which (see kind).
- `--replace <old> <new>` replaces the one place the text `<old>` holds occurs under the title with the text `<new>` holds. Both are sources (`-` for stdin, at most one of them), each losing one trailing newline; it refuses text found nowhere or more than once. They are sources rather than arguments because on Windows the global command is a `.cmd` shim, which cuts an argument at its first newline and mangles quotes; a file keeps every newline and backslash.

`--body`, `--section` and `--replace` refuse a doc with no title, saying to set one first, rather than guessing where its body starts.

`crud --batch <source>` applies a YAML list of edits in order and commits once per repo. Each item names a doc by `quid` and one edit keyed as its flag: `title`, `body`, `gist`, `name`, `kind`, `meta`, `scopes`, `links` and `parent` take the flag's value, `section` takes `{heading, text}` and `replace` takes `{old, new}`. Text is inline, so a block scalar carries any newline or backslash without a file. Each edit refuses as its flag would, naming its item, and then nothing is written, with one difference: a doc's meta is checked against its kind once, after all of the batch's edits to it, so one batch can change a doc's kind and its meta together, as answering a question does. Its commit names the batch's edits (see Commits).

`crud --drop <quid>` deletes a doc's file and commits, and never edits another doc. While any doc in the bridge or a workspace kb links to it (its parent's `child.feat` and its children's `parent.feat` included), or mentions its id in its body, or a config names it as its root, it refuses, naming each; move or remove those first with `--links`. Refusing a doc whose kind is droppable, it ends with that kind's Drop when, quoted whole, as what dropping it takes (drop-when). A doc whose kind is durable (`meta.durable: true` on its kind doc) is refused even then, since its file is what keeps it findable to anyone holding its id; `--hard` deletes it anyway.

`crud --drop-list <source>` drops every doc whose quid `<source>` lists, one per line (`-` for stdin), together in one commit per repo. Only links and mentions from docs outside the list count, and from docs git tracks (a doc git ignores, such as a tool's local copy, is no part of the kb's history), so a set of docs that all mention each other, which no single `--drop` could ever start on, goes at once. `--hard` works as for `--drop`.

## Commits

A commit crud makes reads `feat(<feat name>): crud <what>` (see commit-subject): `<what>` is the kind for a mint, as spelled (`crud core:memo`), the edit's name for an edit (`crud links`), the distinct edits of a batch in order (`crud body, links`), and `drop` for a drop. A doc with no feat to name gets `crud: <what>`; nothing refuses. Each commit ends with the nosedive co-author trailer (see commit-message).

## Writing a doc

A kind belongs to its owner, the repo that declares it, and a doc says whose kind it is. Any other repo that has something to say about the doc says it in its own scope entry.

- **Mint**: a kind that is not that of the repo holding the doc writes `kind: <name>`, and a scope entry `<owner id>: { canonical: true, version: <version>, schema: <digest> }`. The repo's own kind writes no entry. Core's kinds and repos in `.nosedive/` need none, being core's by place; seed's root names core in the same way.
- **Meta**: it belongs to the doc's kind, found in the terms of its holder when that repo is seeded and not the one acting, as seeded repos read their own docs (the holder-terms decision), else in the acting repo's. Docs in a repo that is not seeded are common, and are read as the acting repo reads them. When the doc's kind is its holder's own or the owner its canonical scope names, meta goes to the root's `meta`, checked against that kind's schema. A doc with no owner, in a repo that is not seeded, has its meta kept in this repo's own entry, keyed by its id and carrying the `version` and `schema` digest of the kind it is checked against, created if missing and gone with its meta. A kind that cannot be found refuses, naming it and saying the hero can declare one of that name.
- **Entries**: one for each key; crud refuses a doc whose scopes repeat a key, as it would write it, and an entry that carries a `kind`, since an entry's kind is the root's. They carry `canonical`, `version`, `schema` and `meta`. Work scopes, keyed by a repo doc's quid with a `work-branch` and a `ref` that jump sets, are in the same list, and crud leaves them as they are and applies no version rule to them.
- **Version**: the newest commit that changed the kind's schema in its owner, never one that changed its prose (see find-kind). crud writes a version only when it is on the owner's origin trunk or the work branch a feat's scope names for the owner's repo, and otherwise refuses, naming the kind and saying to land or push it first. It asks the owner's git history whenever it has it, and trusts a build's record that the version was published only where it has none. Every entry crud stamps with a `version` also gets `schema`, a short digest of the schema the version was written against (see find-kind), so that a version a force-push orphaned can later be re-pinned to the commit that now holds the same schema; crud does not re-pin.

## Gates

A kind whose docs must keep a shape links crud gates (see crud-gates). Every write of crud runs them: a mint, an edit, a kind change and a batch run the before gates and then the after gates of each doc they touch, with the doc as it was and as it will be, before committing; a drop runs the before gates of each doc it drops, before anything goes. A gate that refuses or fails stops crud, nothing is written, and a doc minted is removed again.
