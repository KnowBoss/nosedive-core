# Crud

## Usage

`crud` alone lists the kinds there are, as list-kinds finds them: the repo's own kinds, bare, then each cape it wears that declares kinds, core first, with every spelling that reaches each of its kinds.

```text
my-hero
  idea

core
  (core|nosedive-core|01a1336b-c0b8-7cde-b7c6-285196062297):memo
```

Wherever crud takes a `<quid>`, a `--drop-list` line included, a path ending `<quid>.md` is that quid, so the path `next` prints beside a doc names it (listed-paths-accepted).

`crud <quid>` prints a doc: from the bridge's kb, then the repos checked out in its workspace (see locate-kb-doc), then the docs of the capes that are loaded, then those of every cape the bridge wears that has a build for this core, so a cape's own docs, its migrations' included, can be read anywhere it is worn. `crud --read <quid>` finds the doc the same way and prints it to be read (crud-read): its title and body, without its front matter, with each relative markdown link, `[text](target)` or a `[label]: target` definition, rewritten relative to where crud runs, with forward slashes, so it opens from there. A `#fragment` is kept; a target with a scheme (`https:`, or a cross-repo `<repo>:<path>`), an absolute path, a bare `#anchor`, and anything in a code span or a fenced block are left as written. A doc with a file on disk (the hero's, a workspace's, a local cape's, a cape's that runs from a checkout) is rewritten from that file and nothing is docked. A cape's doc with no file, as one from a shipped build or built from a clone is, has its repo docked as `dock` does (read-docks-capes): the hero's repo doc named as the cape, at `~/.nosedive/docks/<docker>/<repo doc name>`, read-only and detached at the commit the cape was built at, and the links are rewritten relative to the doc's file there. A dock already there is used as it is and never moved, whatever its head, since the pilot may have docked it elsewhere; only where there is none is one placed, at the build's commit, `dock`'s refusals kept. `dock`'s own report goes to stderr, so stdout is the doc. The text printed is still the build's, what the hero runs; only its links resolve into the dock. Where the repo cannot be docked (the hero has no repo doc of that name, the fetch fails, `dock` refuses, or the dock, one already there included, does not hold the doc), the links are printed as written and one line on stderr says why; the exit code stays 0. It writes nothing in the hero, but may fetch and check out under `~/.nosedive`.

The edits below find their doc the same way, and commit in the repo it lives in. They refuse a doc git does not track, such as a tool's local copy, before writing anything, since its change could never be committed.

`crud <kind> <gist>...` mints a doc of that kind in the target (see launch's `--at`), the primary root's directory unless another is selected, and commits in the git repo holding it: `nosedive --at workspace/<repo> crud <kind> ...` writes into a checkout, at any directory of it, seeded or not. Docs of core's own kinds, `core:kind` and `core:repo`, go in the hero's `.nosedive/kinds/` and `.nosedive/repos/` instead, and refuse a selected target, since the hero reads its kinds and repos only from there.

A kind is spelled as find-kind takes it. A bare kind is the repo's own and nothing else, so core's memo is `core:memo`; `<short>:<kind>`, `<long>:<kind>` and `<quid>:<kind>` are a cape's, by the name of its cape root doc, the name of the repo doc that registers it, or its owner's seeded id. A spelling no kind answers to is refused, naming those that reach a kind of that name; a bare kind the repo does not declare is refused, naming the kind and saying the hero can declare one of that name, and how a cape that declares it is spelled if one does. A kind doc named `kind` is refused: only core declares the kind of kinds. Its name is `--name`, or the gist's first words slugged with the id's last six characters; its title is made from `--name` when one is given, else the gist (see mint-kb-doc); and its meta is whatever `--meta <source>` reads, with each `--meta:<path> <value>` set over it, so a kind with required meta can be minted. Each `--section:<path> <source>` is written into its body before its kind's crud gates see it, and all of it is the mint's one commit, so `crud work:dive <gist> --meta:feat <feat> --section:Brief -` mints a briefed dive in one command (keyed-flags).

`crud core:repo <gist>... --name <name>` registers a repo, and refuses, writing nothing, unless `--name` is given and unique among the hero's repos, and `meta.remotes.origin` is given and `git ls-remote` reaches it. It makes nothing else: creating a bare repo somewhere is a cape's job.

The `--meta`, `--scopes` and `--links` usages read a YAML or JSON mapping from `<source>` (`-` for stdin) and merge it into that field, then commit:

- `--meta`: a JSON merge patch onto `meta`. `--meta:<path> <value>`, given any number of times, sets one key at its dot path instead, its value read as YAML and `null` removing it (`--meta:feat <quid>`, `--meta:a.b 2`), with any `--section:<path> <source>` in the same commit (keyed-flags).
- `--scopes` and `--links`: keyed by repo or link target, a link to a doc in another repo keyed `<repo>:<path>`, its path in that repo; each value is merged onto that entry, a new key is appended, and `null` removes the entry. An entry the patch does not name keeps its written form, and one left with no fields is written as `{}`.

`--parent <parent>` makes `<parent>` the doc's only `parent.feat`: its other `parent.feat` links go, with those parents' `child.feat` links back to it, and `<parent>` gains a `child.feat` link to it, all in one commit. Both docs must be in the same kb, and a parent that is the doc itself or under it is refused, as is a non-durable parent of a durable doc that is no root (see kind). That rule holds for every edit that adds a `.feat` link, `--links` and `--batch` included (see edit-kb-docs). Each new link is keyed by its target's path from the repo root: `bridge/<id>.md` in a hero repo, `kb/<id>.md` in a cape.

Whatever a doc's kind is, crud checks its `meta` against that kind's schema when it mints the doc, changes its meta, or changes its kind (`--kind <kind>`). The kind is the doc's own (see doc-kind), found in the terms of the repo that holds the doc when that is seeded (see Writing a doc). A kind nothing declares cannot be minted or changed to, and the meta of a doc whose kind nothing resolves is refused too, naming the kind and saying the hero can declare one of that name.

A kind's schema can require a meta field to contain the quid of a doc of a particular kind. For example, `question: {type: string, kind: question}` under `properties` requires that `meta.question`, when present, is text containing a quid resolving to a doc whose frontmatter says `kind: question`; adding `question` to `required` makes the field mandatory. Crud searches the doc's kb and the bridge's kb first, then the hero and its workspace, then loaded capes. An invalid quid, missing doc or wrong kind refuses the write with an error at the field's path. This checks outgoing references when the owning doc's meta is validated; it does not revalidate incoming references when their target changes kind or is deleted.

In a batch, reference-kind validation sees every edited target's final kind, regardless of edit order. A failed reference check writes and commits nothing from the batch.

`--gist <gist>` and `--name <name>` replace those fields; quote a gist of more than one word. `--kind <kind>` takes a kind spelled as a mint takes it, and writes the doc's scopes as a mint would: the canonical one names the kind's owner unless that is the repo that holds the doc, and a canonical one the doc had is gone.

A doc's body is its title, the one `# ` heading that starts it, then everything under it, and crud keeps the title apart so no edit loses it:

- `--title <title>` sets the title, adding one when the doc has none.
- `--body <source>` replaces everything under the title with the text `<source>` holds (`-` for stdin, else a file), as text, not YAML. A source whose first non-blank line is a `# ` heading holds the doc whole: that heading becomes the title, as `--title` would set it, on a doc with none too, and the rest is written under it, so no title is doubled (body-source-title). An empty source leaves only the title.
- `--section <heading> <source>` replaces the `## <heading>` section, up to the next `## `, with that text, or appends it when the doc has no such section; an empty source removes it. On a `kind` doc, `--section "Drop when"` decides the kind's durability: adding the section makes it passing work, removing it makes it durable, and crud says which (see kind).
- `--section:<path> <source>`, given any number of times, writes the section at a dot path of headings, parent first, `##` and one level deeper each step: `--section:Dropped.<id>` is `### <id>` under `## Dropped`. Headings are found in any case, and each one missing is made as spelled, after its siblings. A section is everything under its heading, its subsections too, so writing one replaces them and an empty source removes it. At most one source of a command is stdin; a heading with a dot of its own cannot be named (keyed-flags).
- `--replace <old> <new>` replaces the one place the text `<old>` holds occurs under the title with the text `<new>` holds. Both are sources (`-` for stdin, at most one of them), each losing one trailing newline; it refuses text found nowhere or more than once. They are sources rather than arguments because on Windows the global command is a `.cmd` shim, which cuts an argument at its first newline and mangles quotes; a file keeps every newline and backslash.

`--section`, `--replace` and a `--body` whose source brings no title refuse a doc with no title, saying to set one first, rather than guessing where its body starts.

`crud --batch <source>` applies a YAML list of edits in order and commits once per repo. Each item names a doc by `quid` and one edit keyed as its flag: `title`, `body`, `gist`, `name`, `kind`, `meta`, `scopes`, `links` and `parent` take the flag's value, `section` takes `{heading, text}` and `replace` takes `{old, new}`. Text is inline, so a block scalar carries any newline or backslash without a file; a `body` that starts with a `# ` heading sets the title, as `--body` does. Each edit refuses as its flag would, naming its item, and then nothing is written, with one difference: a doc's meta is checked against its kind once, after all of the batch's edits to it, so one batch can change a doc's kind and its meta together, as answering a question does. Its commit names the batch's edits (see Commits).

`crud --drop <quid>` deletes a doc's file and, in the same commit, the links to it from the docs it hangs from, whichever kb of the bridge or its workspace holds them (drops-recorded, drop-takes-tree-links, drop-takes-declared-links). It refuses, naming each reason, and writes nothing:

- until one of the docs it hangs from has a `### <id>` section under `## Dropped` saying what of it is kept, other than its gist. Whoever drops it writes that, having read it: the refusal names the doc to read and the command, `nosedive crud <parent> --section:Dropped.<id> -`. A doc whose parent is dropped with it needs no record of its own.
- when it hangs from no doc, unless `--sure` is given, since none can record what it held.
- while a doc hangs under it by `parent.feat`: drop that first.
- while any other link names it (a rel that is neither a `.feat` rel nor one its kind names in `meta.next`), as a worn cape's or a spec's does, or a body links it (`<id>.md`), or a config names it as its root; those are removed by hand, since a drop must not undo them unasked. A root of the hero's own that links a `.feat`, whose body is the tree seed renders from its links (see render-tree), is the exception: the drop renders its tree again, in the same commit, once the docs and their links are gone (drops-rerender-tree). A bare id in a body, as a `### <id>` record is, is no link.

The docs a doc hangs from are any tracked doc that links it by a `.feat` rel other than `parent.feat`, or by a rel its kind names in `meta.next` (a non-durable kind's), whether `next` walks that doc or not, and those its own `parent.feat` links name. A drop that removes links reports each on stderr, once the drop has committed, as `unlinked <holder path>: <rel> <dropped doc path>` (paths relative to the bridge, forward slashes), so what changed outside the dropped files is on the record; stdout stays the dropped paths, one per line.

Refusing a doc whose kind is droppable, it ends with that kind's Drop when, quoted whole, as what dropping it takes (drop-when). Once the drop is made, `## Dropped` entries may be pruned or moved freely. A dropped doc is read back from git: `git log --all -1 --diff-filter=D --format=%h --name-only -- '*<id>.md'` names the commit that dropped it and its path, and `git show <commit>^:<path>` prints it. A doc whose kind is durable (`meta.durable: true` on its kind doc) is refused even then, since its file is what keeps it findable to anyone holding its id; `--hard` deletes it anyway.

`crud --drop-list <source>` drops every doc whose quid `<source>` lists, one per line (`-` for stdin), together in one commit per repo. Only links and mentions from docs outside the list count, and from docs git tracks (a doc git ignores, such as a tool's local copy, is no part of the kb's history), so a set of docs that all mention each other, which no single `--drop` could ever start on, goes at once. `--hard` works as for `--drop`, and it prints the links it removed as `--drop` does.

## Commits

A commit crud makes reads `feat(<feat name>): crud <what>` (see commit-subject): `<what>` is the kind for a mint, as spelled (`crud core:memo`), the edit's name for an edit (`crud links`), the distinct edits of a batch in order (`crud body, links`), and `drop` for a drop. An edit is named for its flag, so a `--body` that sets the title is still `crud body`. A doc with no feat to name gets `crud: <what>`; nothing refuses. Each commit ends with the nosedive co-author trailer (see commit-message).

## Writing a doc

A kind belongs to its owner, the repo that declares it, and a doc says whose kind it is. Any other repo that has something to say about the doc says it in its own scope entry.

- **Mint**: a kind that is not that of the repo holding the doc writes `kind: <name>`, and a scope entry `<owner id>: { canonical: true, version: <version>, schema: <digest> }`. The repo's own kind writes no entry. Core's kinds and repos in `.nosedive/` need none, being core's by place; seed's root names core in the same way.
- **Meta**: it belongs to the doc's kind, found in the terms of its holder when that repo is seeded and not the one acting, as seeded repos read their own docs (the holder-terms decision), else in the acting repo's. Docs in a repo that is not seeded are common, and are read as the acting repo reads them. When the doc's kind is its holder's own or the owner its canonical scope names, meta goes to the root's `meta`, checked against that kind's schema. A doc with no owner, in a repo that is not seeded, has its meta kept in this repo's own entry, keyed by its id and carrying the `version` and `schema` digest of the kind it is checked against, created if missing and gone with its meta. A kind that cannot be found refuses, naming it and saying the hero can declare one of that name.
- **Entries**: one for each key; crud refuses a doc whose scopes repeat a key, as it would write it, and an entry that carries a `kind`, since an entry's kind is the root's. They carry `canonical`, `version`, `schema` and `meta`. Work scopes, keyed by a repo doc's quid with a `work-branch` and a `ref` that jump sets, are in the same list, and crud leaves them as they are and applies no version rule to them.
- **Version**: the newest commit that changed the kind's schema in its owner, never one that changed its prose (see find-kind). crud writes a version only when it is on the owner's origin trunk or the work branch a feat's scope names for the owner's repo, and otherwise refuses, naming the kind and saying to land or push it first. It asks the owner's git history whenever it has it, and trusts a build's record that the version was published only where it has none. Every entry crud stamps with a `version` also gets `schema`, a short digest of the schema the version was written against (see find-kind), so that a version a force-push orphaned can later be re-pinned to the commit that now holds the same schema; crud does not re-pin.

## Gates

A kind whose docs must keep a shape links crud gates (see crud-gates). Every write of crud runs them: a mint, an edit, a kind change and a batch run the before gates and then the after gates of each doc they touch, with the doc as it was and as it will be, before committing; a drop runs the before gates of each doc it drops, before anything goes. A gate that refuses or fails stops crud, nothing is written, and a doc minted is removed again.
