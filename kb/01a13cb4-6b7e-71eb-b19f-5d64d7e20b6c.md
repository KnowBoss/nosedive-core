# Base

`nosedive seed` makes one: `base` is the default root kind. Only a base has a workspace, at the path its root's `meta.workspace` gives (`./workspace` when seeded). Seed makes the folder, with a `.gitignore` of `*` inside, so nothing checked out there is committed and the repo's own `.gitignore` is left alone; when the path changes, the next seed moves the workspace. Writing a doc into a repo checked out there, with `crud <repo>:<kind>`, refuses anywhere else.

Any other seeded repo is nosedive-aware without being a base: a cape, or an implementation repo with a kb. A base learns what such a repo is when it checks it out, from the kind of its root.

## Its own actions

A base can carry actions and functions of its own, in its kb and `src/` as a cape does, which scaf scaffolds and the check checks. They are the base's alone: no other bridge can add them, as it can a cape. Its commands run as `nosedive <name>` from the base or its workspace, and help lists them under the base's name, after core's; its gates are among those pass reaches.

Its code is built from the working tree, not from a commit, into `.nosedive/capes/<id>.js`, with `<id>` covering the core and every code doc and file, so an edit is built on the next run that needs it. It imports from core only.

Open: every run that needs the base's code, each `pass`, `help` and any command core lacks, finds its code docs by reading the head of every doc in its kb, which grows with the kb. Its `src/`, whose files are named by doc id, could say which docs to read instead, at the cost of a doc with no files yet being no part of the build.
