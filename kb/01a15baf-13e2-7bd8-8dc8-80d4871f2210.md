# Hydrate repo

Every checkout is a worktree of the user's cache of its repo, a bare repo under `~/.nosedive/cache/` (`$NOSEDIVE_USER_DIR/cache` when that is set, as the tests do), shared by every checkout of every hero, so one fetch serves them all.

The cache is keyed by the repo's origin, not by its repo doc, so heroes that register one remote under different doc ids share one cache (user-cache-by-remote). The key is the origin as `remoteKey` spells it: scheme, user, port, `.git` and trailing slashes gone, the host in lower case, so `git@github.com:Owner/Name.git` and `https://GitHub.com/Owner/Name/` are both `github.com/Owner/Name`. The cache is at `cache/<host>/<hash>.git`, the hash being the first 16 hex digits of the key's sha256: caches are grouped by host, and no path in a key can put one cache inside another's directory. An origin that is a local path, resolved against the hero as it is fetched, is at `cache/_local/<hash>.git`, and one whose host is no plain name (letters, digits, `.` and `-`) at `cache/_other/<hash>.git`; no host name holds `_`, so neither group can be a host's.

Azure DevOps serves one repo under four spellings, and `remoteKey` reads them as one, `dev.azure.com/<org>/<project>/<repo>` in lower case, as Azure's names are: `dev.azure.com/<org>/<project>/_git/<repo>` over https, `ssh.dev.azure.com:v3/<org>/<project>/<repo>` over ssh, and the older `<org>.visualstudio.com/[DefaultCollection/]<project>/_git/<repo>` and `vs-ssh.visualstudio.com:v3/<org>/<project>/<repo>`. Each is matched whole, so a shape Azure adds later keys as itself and costs a second cache, never a cache shared with another repo. Any other host's key is its spelling: two remotes it serves one repo under are two keys and two caches.

Each cache records its key in its git config, `nosedive.key`, when it is first fetched; one at a key's path that holds another key is refused, naming both, so a hash two keys share can never put two repos in one cache. A cache has one origin and is fetched with `--prune`, so only repos with one key may share it; changing a repo's origin starts a new cache.

A cache kept the old way, at `cache/<repo doc id>.git`, is moved to its key the first time it is wanted, when nothing is at the key yet, and `git worktree repair` run in it so its checkouts follow (ship-caches-move). One that cannot be moved is used where it is, with a warning saying why. When a cache is at the key already, an old one is left as it is, with a warning naming it: its checkouts are git's to serve until they are removed, and every new checkout comes from the keyed cache. Checkouts live only in a workspace, at `<workspace>/<name>`. It takes the hero, the repo's doc and, optionally, a feat: the feat's id and the scope's work branch. It returns the checkout's directory and the repo's trunk, `meta.trunk` or else the branch origin's HEAD names. The work loop checks out every repo a dive scopes this way.

Each hydrate first fetches `meta.remotes.origin` into the cache, its branches as `origin/*` and its `refs/nosedive/*` as they are. With origin unreachable it warns and goes on with what the cache has; with no cache either, it refuses. The cache alone owns the trunk branch, and each fetch fast-forwards it; a trunk that has moved apart from origin is left as it is, with a warning. A cache with per-worktree config on tells each new worktree it is not bare.

Given no feat, the checkout is detached at trunk, read-only: it has no branch to push. Given a feat, it is on the local branch `<hero id>/<hero branch>/<feat id>`, the hero branch being the one the hero's own checkout is on; a detached hero is refused. The cache's branch of that name is reused when there is one; otherwise it starts at the work branch on origin, else at trunk; where a cape keeps a feat's work between checkouts, such as the work cape's dive refs, is the cape's to restore. Either way it tracks the work branch on origin.

A repo holds one checkout at a time: one already there is left as it is when it is what was asked for, and refused otherwise, naming the branch it is on, or that it is detached.
