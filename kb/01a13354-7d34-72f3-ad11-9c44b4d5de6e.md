# Action

An action doc is the way into a cape's code: find the action in its repo's root tree, read its doc, then go to the files its id and usages name. What other code calls, and users cannot, is a [function](01a144bf-815a-7e22-ab7d-9f7bbb727bca.md). Both carry code, and their kind decides its signature.

## Fields

- `name`: what users type (`crud`, `cape`).
- `gist`: one line on what it does.
- `meta.usages`: the contracts it supports, in docopt notation: `<arg>`, `<arg>...` (one or more), `[ ... ]` (optional), `--flag`, `--option <value>`. Each starts with the name, which makes the action a command, or each starts `pass --<sect> <kind>`, which makes it a gate; an action is one or the other. A value of `-` means stdin, by convention of the impl that reads it.

```yaml
meta:
  usages:
    - crud <quid>
    - crud <quid> --meta <source>
```

The body says what the action is for and how to use it.

## Commands and gates

A command is what users type: help lists it, and `nosedive <name>` runs it. A gate is what a doc passes through: `nosedive pass` reaches it by its usages, which start `pass --<sect> <kind>`, never by its name, and only `pass --help` lists them. `<kind>` is the kind of doc the usage takes, or `<quid>` for any. A doc, or its kind for every doc of it, links the gate as `<sect>.gate`: the cape kind links core's cape-tests-pass as `test.gate`, so `nosedive pass --test <root>` runs any cape's tests. What a gate's usage impl gets, and how pass runs it, is in [pass](01a14b30-ee4e-722f-961d-32bbb99bdb8a.md).

Each usage of a gate is one shape of command line, and only gates with a usage the command line matches run: `pass --ready <device>` and `pass --ready <device> --deep` are two usages, while one usage with an optional `[--deep]` runs with or without it.

## In the tree

The repo's root links each action as `rel: actions.feat`, and each doc links back to its one parent with `rel: parent.feat`, its parent linking it as `rel: child.feat`, so every doc has exactly one place in the tree. A function hangs under the action or function that uses it only while that is its only user. Once a second one imports it, it moves to a lib group: a memo the root links as `rel: lib.feat`, such as `kb`, `ids`, `repos` or `capes`. Moving one changes links only, never code: `src/` is flat and named by id.

## Files

Everything with code lives in `src/i<id>.ts`, exporting `i<id>`, its implementation. With `h` = an action's doc id without dashes, and `u` = `uuidv5(<usage text, whitespace collapsed>, <doc id>)` without dashes:

| File | Exports | Holds |
|---|---|---|
| `src/i<h>.ts` | `i<h>(call: ActionCall)` | Routes the matched usage to its implementation; a gate's call carries its `GateCtx` as `call.gate`. |
| `src/i<u>.ts` | `i<u>(args, ctx)` | One usage's implementation: a function with plain arguments, or, for a gate's usage, `i<u>(ctx: GateCtx)`. |
| `test/t<u>.test.ts` | | That usage's tests, driven through the launcher with real arguments, so they prove the usage is reachable. A gate's usage has none: a gate is a test. |

Code imports another doc's code by its export, named for what it does where it is used: `import { i01a1335482437c9eb145885f65f12aa1 as matchUsage } from "./i01a1335482437c9eb145885f65f12aa1.ts"`. To learn what one does, read `kb/<its id, dashed>.md`. From another cape, the module is that cape's repo name, `nosedive-core` for core, and the importing doc must link what it imports as `<repo>:<doc id>`.

Rewording a usage changes `u`, so its implementation and test must move: a contract never changes silently. `nosedive scaf` writes the missing files with the signature each kind calls for; the check refuses an action without usages, and any file no doc accounts for.

## In a cape

A cape exports `id`, `name`, `commit`, `version`, `docs` and `index`, and, when built by seed, the `core` and the capes it `needs`. With `K` the cape id, `index[uuidv5(<name>, K)]` is the doc id of the action named `<name>`, and `index[uuidv5(<doc id>, K)]` is that doc's code. `K` covers the commit, the core and every cape imported, so code built against another build never finds a stale entry.
