# Find kind

A kind is its owner's seeded id and its name, and a spelling names one in the terms of the repo acting:

- A bare name is the repo's own kind, declared in its `.nosedive/kinds/`. Nothing else: no fallback to the capes it wears or to core, so `memo` is `core:memo`.
- `<short>:<name>` names a kind of a cape the repo wears, the short name being the name of the cape's root doc, `core:memo` or `work:dive`.
- `<long>:<name>` does so by the long name, the name of the repo doc that registers the cape, `nosedive-work:dive`.
- `<quid>:<name>` does so by the owner's seeded id, which also reaches the repo's own kinds.

When two capes share a short name neither short name reaches a kind, and both are reached by long name; when the long names clash too, by quid. What a spelling reaches is list-kinds'. Nothing else is looked at, and a spelling that reaches no kind returns nothing; `unknownKind` says why, naming the spellings that reach a kind of that name, and `undeclaredKind` does so for a bare name the repo does not declare, which is refused because only the hero can declare it.

It returns the declaration's meta: its `schema`, its `dropWhen` when its doc has a `## Drop when` section (or a legacy `## Done when`), the section's whole text, its `links`, which name the gates its docs pass through, its `id`, `name` and `owner`, its `version` and the `digest` of its schema. Check-meta validates against the schema; `isDurable` reads whether docs of the kind are kept: a declared kind with no `doneWhen` is durable, and a doc whose kind nothing declares is not, which crud's `--drop`, edit-kb-docs and next ask; crud's mint sends core's `kind` and `repo` to `.nosedive/`.

`kindOfDoc` answers what a doc's kind is for a reader: its doc-kind, the terms to read it in, which are its holder's when that is a seeded repo other than the one acting (a doc in a workspace checkout means what its checkout's own kinds say, with core's), else the acting repo's, and the kind's declaration in those terms.

A kind's version is the newest commit that changed `meta.schema`, never one that changed its prose. A build records it beside each kind (see describe-cape-source); a kind of the hero's own, or of a cape run from source, has it walked from its doc's history in git by `versionOf`. A schema that is not committed has none. `assertPublished` accepts a version only when it is an ancestor of its owner's origin trunk, or of the work branch a feat's scope in the hero names for the owner's repo doc, and otherwise refuses, naming the kind and saying to land or push it first. Where the owner's git history is here (a checkout of it, the cape's source, `workspace/<long name>` or the build's clone, as list-kinds found it), `assertPublished` asks that history and nothing else, so a version that is not on the trunk is refused though a build said it was. Only where there is no history at all does it trust the build's record of whether the version was on the trunk then, which stays true, so a hero need not hold a cape's or core's history to name its kinds; with neither it refuses.

A scope entry that carries a `version` carries `schema` beside it: a short digest of the kind's schema, the first 12 hex characters of the sha256 of the schema serialised with its keys in order, so the same schema always has the same digest (`schemaDigest`, in describe-cape-source). A build records it for each kind, so `digestOf` has it without history. It is there so that a version a force-push orphaned can later be re-pinned to the commit that now holds a schema with the same digest; nothing re-pins yet. `pinOf` answers both, `version` and `schema`, for the entries crud and the migration write.
