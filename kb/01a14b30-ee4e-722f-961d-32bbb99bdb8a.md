# Pass

## Usage

Behaviour that belongs to a kind lives in gates, not in crud or a command of its own. `nosedive pass --<sect> <quid> ...` runs every gate linked as `<sect>.gate` that has a usage the command line matches, first from the doc's kind doc, then from the doc, each in link order and each once. A rel is `<sect>.<role>`: the role says what the target is to the doc, the sect which of them.

pass knows no sect itself. It takes its command line as it is, and matches it against the docopt usages that the gates of core, of the hero, and of every built cape declare, each starting `pass --<sect> <kind>`. The sect's own option takes the passing doc's quid, and a usage matches only a doc of its kind, read as find-kind does in the hero's terms except that a bare kind is the declaring cape's own, or any doc when it says `<quid>`. `pass` or `pass --help` lists those usages, and a command line none matches is refused with them. Of the gates the doc and its kind link in the sect, each with a usage that matches runs, getting what that usage binds besides the sect's option; when none has one, pass refuses, naming the kinds the sect's usages take.

pass calls each gate's entrypoint with the usage it matched, as any action is called, and with `call.gate`, a `GateCtx`: the core, the other loaded capes, the bridge, the doc, the args its usage bound, the pass's edit, `crud` to edit docs in it, and `out`/`err`. Gates run in order and the first that throws stops the pass. They edit docs through the pass's edit, with crud-edit, so when all pass, each repo gets one commit, `pass(<name>): <sect>`, and when one fails nothing is written. `pass --test <cape>` on a cape's root runs its tests, since the cape kind links core's test gate.
