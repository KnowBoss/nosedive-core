# Pass

## Usage

Behaviour that belongs to a kind lives in gates, not in crud or a command of its own. `nosedive pass --<sect> <quid> ...` runs every gate linked as `<sect>.gate` that has a usage the command line matches, first from the doc's kind doc, then from the doc, each in link order and each once. A gate is the last quid of its link's key, so a gate in another repo's cape is linked as crud keys it, `<repo id>:kb/<gate>.md` (repo-cape-gate-links); crud gates are found the same way. A rel is `<sect>.<role>`: the role says what the target is to the doc, the sect which of them.

pass knows no sect itself. It takes its command line as it is, and matches it against the docopt usages that the gates of core, of the hero, and of every built cape declare, each starting `pass --<sect> <kind>`. The sect's own option takes the passing doc's quid, or the path of a local cape (see local-capes), which pass reads as the quid of its root, and a usage matches only a doc of its kind, read as find-kind does in the hero's terms except that a bare kind is the declaring cape's own, or any doc when it says `<quid>`. `pass` or `pass --help` lists those usages grouped by the kinds that link their gates (pass-groups): a group for each kind, named by the kind's spelling as `crud` spells it (`memo`, `question`, `core:cape`), in name order, each kind once, holding the usages of every gate it links as `<sect>.gate`, sorted; a usage two kinds link is under both. The usages no kind links come last under `any doc`. A command line no usage matches is refused with the same list. As for any action, each usage in the listing is followed by the summary of its jsdoc block; `pass --help --more` adds under each its `@nosedive-` attributes as `<key>: <value>` lines and its hash, `u<first 8 hex of its id>`, then this section, then says that `nosedive pass --help --more <u-hash>` prints the rest; `pass --help --more u<hash>`, a prefix of at least 4 hex digits being enough, prints the block of that one gate usage, and refuses an unknown or ambiguous prefix, naming the usages (see launch). pass reads its own `--help`, being given the command line as it is.

```text
memo
  pass --ask <quid> <source>

any doc
  pass --turn <dive> [<summary>]
``` Of the gates the doc and its kind link in the sect, each with a usage that matches runs, getting what that usage binds besides the sect's option; when none has one, pass refuses, naming the kinds the sect's usages take.

pass calls each gate's entrypoint with the usage it matched, as any action is called, and with `call.gate`, a `GateCtx`: the core, the other loaded capes, the bridge, the doc, the args its usage bound, the pass's edit, `crud` to edit docs in it, `mint` to mint a doc into a kb directory for the pass (as mint-kb-doc, added to git's index as intent-to-add so the edit finds it), and `out`/`err`. Gates run in order and the first that throws stops the pass. They edit docs through the pass's edit, with crud-edit, so when all pass, each repo gets one commit, `feat(<feat name>): pass <sect>` (see commit-subject), `pass: <sect>` when the doc has no feat to name, and when one fails nothing is written. Nor is anything left when the commit itself refuses, as its durable-link check does: every doc a gate minted is taken out of git's index and deleted, whatever failed (gate-mints-roll-back).

A cape the hero wears that has no build for the running core, as after core is rebuilt and before seed, has no gates in the pass; its listing, and the refusal of a command line no usage matches, end with it under its name, `not built: run \`nosedive seed\`, until then its gates are missing`, as help shows it, so its gates are never silently absent (unbuilt-said). `pass --test <cape>` on a cape's root runs its tests, since the cape kind links core's test gate.
