# Seed

## Usage

On a repo it knows, seed first brings it to today's shape by running the migrations it has not run (see run-migrations), and runs them once more after it has built the capes, so a migration that waited for a cape to build (canonical-kinds) runs in the same seed. `--no-capes` builds none, so that second run is only a retry. On a repo nosedive does not know yet, seed writes `.nosedive/config.yaml` with `migrations` listing every migration there is, since a new repo is already in today's shape, and one root, `self/<quid>.md` with `--workspace` and `kb/<quid>.md` otherwise, named after the repo, whose quid is also config `id`: its primary root. The root's kind is one of core's, so its doc names core in a canonical scope, `canonical: true`, the version of that kind and the `schema` digest of its schema, as `pinOf` gives them (see find-kind). Seed refuses, writing nothing, when that version is not published. It is the kind `--root-kind` gives, else `hero` with `--workspace` and `base` without it; an explicit `cape` root stays in `kb/`, even with a workspace, and makes a repo that makes its own actions. Existing roots keep their configured directories; the hero-self migration changes only an existing hero primary root of core kind base to core kind hero. `--workspace` also adds `workspace: ./workspace`. When it enables work on an existing repo, it makes hero-self pending again, even if that migration previously ran as a no-op for a data repo; the retry after setup promotes a primary core base to hero while preserving its path and leaving a cape root untouched. It ignores `cache/`, `capes/` and `local/` in `.nosedive/.gitignore`, leaving the repo's own `.gitignore` alone but for one line in a repo with a cape root or a workspace, `!package-lock.json`: their packages build from the lockfile, which a user's global ignore could otherwise hide from every commit. A repo with no `README.md` gets one, its H1 the repo's name linking to its primary root. Then it commits. Seed makes a workspace's folder with a `.gitignore` of `*` inside it; if the path has changed since the last seed, it moves the folder there. On a repo it knows, it adds whatever of that is missing and leaves everything else alone.

Each root's body, but a local cape's (the cape renders its own when seed runs in it), is its tree, which seed renders on every run and commits when it changed (`seed: <repo> tree rendered`): its title, then a `## ` section for each rel group of its `<group>.feat` links, and under each doc the docs it links as `child.feat`, to any depth, whatever their kinds. `--no-capes` does not skip it.

Then it builds every cape the target root wears that the bridge has not built for the core that is running: a pinned commit once, an unpinned ref at whatever its remote has now. `--no-capes` skips that. A new core means a new build of each cape; that is seed's job, and `pass --attach-cape` only builds the one it attaches. Seed builds every cape it can before failing on those it could not, naming each and why, and, when the manifest says which core last built one, how to get back to it: pin the cape at that commit with a `ref` on its `.cape` link, or run that core. It never goes back on its own. Capes may declare actions core or other capes declare: the launcher resolves shared names (see launch).

Last, with or without `--no-capes`, and before it reports the capes it could not build, seed writes the hero's command surface, `help` as the hero now sees it, into every agent instruction file of its directory that holds the managed markers, stamped with core's version, and commits what changed on its own, `seed: <repo> agent surface written` (see agent-surface). A file that also holds the pilot's uncommitted edits outside the block is written but not committed, and seed says so. A failure writing the surface is reported with the capes that failed to build, never in place of them. It creates `AGENTS.md` with the block when no instruction file exists, and when files exist but none is marked, it prints the hint naming the files and the two marker lines. Seed writes it only in a hero, a repo with a workspace at the top of its own git checkout, so seeding a cape, core included, a base, or a local cape, with `--at` or from inside it, writes none: they are not worked in from their own roots.

`--at <dir>` (see launch) seeds a directory of the hero in place of the hero: a local cape, as `nosedive --at capes/spec seed --root-kind cape` (seed-local-cape, local-cape-shape). Its config and its root are written inside that directory, which gets no `.git` of its own; the files are committed in the hero's git, as `seed: <directory name> set up`, together with the hero's config, whose `roots` gain the cape's root doc path from the hero (`<dir>/kb/<quid>.md`) (cape-roots). The directory is made when it does not exist. Seed refuses, writing nothing, an `--at` that names one of the hero's roots, a directory outside the hero, in its workspace or in its `.nosedive`, inside or holding another root's directory, or inside a directory seeded on its own (a nested repo or another cape), and a directory seeded and registered already. A directory already seeded whose cape root the hero's config does not list is registered by the same command instead: the root's path is appended to `roots` and committed as `seed: <name> registered`, which is how a cape made before roots listed it joins the hero. Without `--at`, seed acts on the nearest seeded repo above where it runs that lies inside the git checkout it runs in, so inside a seeded cape directory it acts on that directory, and an unseeded repo nested under a seeded one (a clone in a workspace) is seeded itself, never the outer hero. The new cape is worn by nothing yet: `pass --attach-cape <dir>` links it from the hero (see attach-cape).

Seed's commits and its migrations' keep their `seed: ...` and `migrate: ...` subjects, since they change the repo, not a feat's work, and end with the nosedive co-author trailer like every commit nosedive makes (see commit-message).
