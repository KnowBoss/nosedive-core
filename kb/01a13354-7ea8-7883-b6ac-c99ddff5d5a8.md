# Seed

## Usage

On a repo it knows, seed first brings it to today's shape by running the migrations it has not run (see run-migrations). On a repo nosedive does not know yet, seed writes `.nosedive/config.yaml` with `last-migration` naming the last migration there is, since a new repo is already in today's shape, and one root, `kb/<quid>.md`, named after the repo, whose quid is also config `id`: its primary root. The root is of the kind `--root-kind` gives, else `base` with `--workspace`, which also adds `workspace: ./workspace`, else `root`; `cape` makes a repo that makes its own actions. It ignores `cache/`, `capes/` and `local/` in `.nosedive/.gitignore`, leaving the repo's own `.gitignore` alone but for one line in a repo with a cape root or a workspace, `!package-lock.json`: their packages build from the lockfile, which a user's global ignore could otherwise hide from every commit. A repo with no `README.md` gets one, its H1 the repo's name linking to its primary root. Then it commits. Seed makes a workspace's folder with a `.gitignore` of `*` inside it; if the path has changed since the last seed, it moves the folder there. On a repo it knows, it adds whatever of that is missing and leaves everything else alone.

Each root's body is its tree, which seed renders on every run and commits when it changed (`seed: <repo> tree rendered`): its title, then a `## ` section for each rel group of its `<group>.feat` links, and under each doc the docs it links as `child.feat`, to any depth, whatever their kinds. `--no-capes` does not skip it.

Then it builds every cape the selected base wears that the bridge has not built for the core that is running: a pinned commit once, an unpinned ref at whatever its remote has now. `--no-capes` skips that. A new core means a new build of each cape; that is seed's job, and `pass --don-cape` only builds the one it puts on. Seed builds every cape it can before failing on those it could not, naming each and why, and, when the manifest says which core last built one, how to get back to it: pin the cape at that commit with a `ref` on its `.cape` link, or run that core. It never goes back on its own. Capes may declare actions core or other capes declare: the launcher resolves shared names (see launch).
