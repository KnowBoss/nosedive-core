# Cape

A repo is a cape when one of the roots its config lists is of this kind: `nosedive seed --root-kind cape` makes one. The feats that root reaches are what the cape does: its actions, which scaf scaffolds and seed builds; a repo with two cape roots has the actions of both. The root's name, which seed takes from the repo folder, is the cape's name: a hero registers the repo by it with `crud repo` and attaches it with `pass --attach-cape`. Only a cape is put on or built by seed, and scaf scaffolds only a cape; any other repo is refused, so a base cannot wear a repo that merely has a kb.

The kind links core's cape-tests-pass as `test.gate`, so `nosedive pass --test <root>` runs any cape's tests.

It also links attach-cape and detach-cape as `attach-cape.gate` and `detach-cape.gate`, for a local cape: a cape seeded in a directory of the hero (`nosedive --at <dir> seed --root-kind cape`), which lists its root in the hero's config roots, is worn with `pass --attach-cape <dir>`, and put off with `pass --detach-cape <dir>`.

The schema is closed and declares nothing yet. What is true of a cape as a whole, rather than of one action, belongs here: in time, whether it is paid, the crew it is built for, the cores it supports.

## Its own actions

Where a cape is itself the bridge nosedive runs in, its actions run there as `nosedive <name>`, and help lists them under the cape's name, after core's; its gates are among those pass reaches. They are built from the working tree, not from a commit, into `.nosedive/capes/base-<id>.js`, with `<id>` covering the core and every code doc and file, so an edit is built on the next run that needs it. Every run that needs that code learns which docs are code from `src/`, whose files are named by doc id, and reads only those; a doc with no files yet blocks nothing until scaf writes them.
